# AGENTS.md — fyr

Project rules for this repo. They override the global context, which this repo is the source of (`context/`).

## What this repo is

The agent harness: one global context (agents.md standard), skills (Agent Skills `SKILL.md` standard), subagents, and `fyr`, the Go binary that installs them into the Antigravity CLI. No hooks, no gates, no CI.
`fyr` is also the second brain the Antigravity CLI consults at the moments the context names (search, memory, metrics, dream): the purpose and its two constraints are `REQUIREMENTS.md` R0.

## How the harness works

The map in `README.md` § How it works defines how the harness reaches a machine and how experience comes back. It is the contract, not an illustration, and these rules are strict:

1. **Three ways in, no way back, nothing else.** A place gets the harness from a checkout kept current with `fyr update`; from a release binary with the harness built into it, installed with `fyr install` and moved forward by `fyr update`; or, as a zip place, from a repository zip the operator downloaded by hand and passes to `fyr update --from-zip <file>` (what each kind of place fetches: rule 6's one home). Experience does not come back: it stays on the machine that logged it, and a harness-target proposal reaches this checkout only through `/retro --harness`, run by the operator on that machine (ADR-062). No service, no push to a machine, no copy vendored into a project, no timer as the mechanism (R8, R9, ADR-030, ADR-033, ADR-038, ADR-062). The nightly dream timer (R3's exception, ADR-047a) is neither: it moves no harness onto a machine, sends each project's redacted content only to the model of the CLI the machine already uses — the one thing that leaves the machine — and its harness-target proposals wait under `~/.config/fyr/proposals/dream/harness/` for the operator's own hands.
2. **A tag is a release.** `/preflight vX.Y.Z` makes an annotated tag and publishes that tag's binaries and a zip of its tree, with their checksums — no key signs anything (ADR-053); what each kind of place does with it is rule 6's one home (D18 of the release-binary plan, ADR-033 superseding ADR-031 D3).
3. **Changing a path is a design question.** Adding, removing or rerouting any line on the map goes to the operator first, gets an ADR, and lands in ONE commit with the code, the docs and the map. A change to install, update or release behaviour whose diff does not touch the map is incomplete; `/review --docs` checks for it.
4. **Dashed means a gap, and it stays honest.** A dashed line is done by hand or limited to one machine; it turns solid in the commit that closes the gap, and nothing is drawn solid before it works for every place. The one exception is the dreamer's olive line to the model provider: dashed because it is not a harness path at all (ADR-049), and it never turns solid.
5. **The map is pinned by a test.** `TestHarnessMap` fails when the map is missing, when it names a `fyr` verb the binary does not have, or when install, update or dream is missing from it, and when it still names `report` or the feedback repository. The interactive page of the map (a private artifact page, not in this repository) is only a view: when the map changes, the page is updated from it, and it is never the source.
6. **The delivery claim has one home.** What a tag delivers, to which kind of place, and how a place moves forward is stated once, in `.agents/docs/specs/fyr/delivery.md` § The model; README's prose, this file, the deploy guides and the ADRs point at it in one sentence and never restate it; the README map draws the paths and its labels name them, which is not a restatement, and a guide or README row describing what a COMMAND does at a place (`update` fetches, verifies, replaces, reinstalls) is that command's documentation, not the claim — rule 6 is about which place gets what from a tag, never about how a command works. A change to the claim is one file, plus the map's lines when a path moves (rule 3; why: `.agents/docs/retros/2026-09-18-retro-2.md`).

## Setup commands

```bash
gofmt -l cmd internal && go vet ./... && go test -race -timeout 30m ./...   # before any completion claim; gofmt takes the source dirs, not `.`, because it walks .agents/scratch and the Go tool does not (BUG-048); -timeout 30m because on a one-CPU box cmd/fyr takes ~13 min under -race, past Go's 10-minute default
# a change to context/*.md or rules/*.md must also pass the two size pins in internal/harness/size_test.go (part of `go test ./...`
# above): TestRenderedContextFitsAntigravityBlock, under 22,000 bytes inside Antigravity's 24,000-byte block (ADR-035), and
# TestRenderedContextUnderTarget, the hand-written context (the render before its generated `## Installed` inventory) under 15,000 bytes, the harness's own ceiling and the only one (plan audit-fix D2b; the goal struck by D10 of plan 2026-10-25-harness-audit-fix); the inventory grows with every skill dropped in and counts only toward the 22,000
go run ./cmd/fyr install --home .agents/scratch/home       # exercise the installer against a scratch home (gitignored)
go run ./cmd/fyr list                                   # sanity-check skills and agents parse
go mod download                                         # once per version, while online: the one module (modernc.org/sqlite, R4) for an offline build later
"$(go env GOPATH)/bin/govulncheck" ./...               # by its full path: GOPATH/bin is not on every shell's PATH, and two review agents skipped it for that (2026-10-09). On go1.27.2: no finding the code reaches (2026-10-09); known in required modules: GO-2026-5024 (golang.org/x/sys via the SQLite driver, not reachable; ADR-045a) and, on a Go before 1.25.12, GO-2026-4970 (os.Root.Open, reached from internal/search but guarded by an Lstat first); older Go also reports two stdlib advisories (see below) — watch for NEW ones
```

`go.mod` carries NO `toolchain` directive, deliberately (ADR-029: a pin makes the module unbuildable offline). On a Go older than go1.24.6 or go1.25.8, `govulncheck` reports two standard-library advisories (`os`, `os/exec`); the fix is upgrading the machine's Go, never pinning it here. The Linux box runs a user-level go1.27.2 SDK (`~/.local/bin/go`) ahead of `/usr/local/bin/go` and `/usr/bin/go` (`.agents/docs/deploy/local.md` § Operator steps).

## Layout

```
context/AGENTS.md      the global context — single source, deployed to ~/.gemini/config/rules/AGENTS.md
context/dev-setup.md   environment, stack, GCP defaults — appended to the context at install
agents/<name>/agent.md subagents in Antigravity's agent.md format, installed as written (nothing derived, ADR-062)
skills/<name>/         skills; .agents/skills is a symlink here so `npx skills add` lands in skills/
skills/google-catalog/catalog/  Google-published skills vendored at a pin (counts, exclusions, notes: its MANIFEST.md), reached through the google-catalog router, never installed as skills
commands/, rules/      markdown prompts invoked as /name, and always-on rules; both deploy verbatim (workflows/ and rules/ under ~/.gemini/config), and rules share the Antigravity block (commands/ empty by design, operator 2026-09-30; rules/ holds critical-thinking.md (ADR-050) and session-sizing.md (ADR-058))
cmd/fyr, internal/harness   the binary and its tests
embed.go, *_test.go    package `fyr` at the root: the `go:embed` of the five content directories (it cannot reach a parent, so it sits here) and the tests of the tree beside it (the embed pinned both ways to git, the init-project assets, the plan)
internal/search        `fyr search` and `index`: the SQLite index (one of the three packages that import the driver, with `internal/metrics` and `internal/brain`); also the dream job's two read-only SQLite reads (the global index's project list, Antigravity's conversation databases, from copies)
internal/memory        `fyr memory add|show`: the project memory store every session uses (R10)
internal/redact        the credential redactor (needles, key blocks) `fyr dream` runs on every input before its prompt leaves the machine; stdlib only
internal/trail         the git reads every package makes into a project root (`trail.Command`, `Dates`, `Log`, `DocsRoot`), shared by search, memory, dream and metrics so neither imports another; no SQLite
internal/dream         `fyr dream`: the background dreamer, its state, lock, log and nightly timer (R3's exception)
internal/metrics       `fyr metrics`: the metrics store, ~/.config/fyr/metrics.db, a store of record of every session's shape (R4, ADR-055)
internal/brain         `fyr record` and search's record hits: the brain store, ~/.config/fyr/brain.db, every project's trail records and the global ones, exported per project to .agents/trail.jsonl (R4, R7, ADR-063; spec .agents/docs/specs/fyr/record.md)
.agents/docs/          this repo's own trail (plans, changes, architecture/DECISIONS.md, reviews, testing, deploy/{local,remote,gcp}.md, bugs/INDEX.md, handoffs, retros, specs/fyr)
.agents/scratch/       gitignored scratch space; every generated or temporary file goes here, never /tmp
```

Nothing generated is committed. The deployed files are assembled by `fyr install`.

## Rules for working here

- The installer must never run against the operator's real `$HOME` during development. Use `--home .agents/scratch/<name>` for every test (the global scratch rule: never `/tmp`). Deploying to the real home is the operator's job.
- `fyr install` rebuilds the binary from its own git checkout with `go build` and lets that build install (BUG-006); the running binary is copied only when `go` is missing, when the tree is a plain copy with no `.git` (whose binary was built from that same tree and which may be read-only to the installing user, BUG-015), or when the source is the harness embedded in a release binary, where there is nothing to build from (ADR-033, D13). After a change under `cmd/` or `internal/`, `fyr status` from the target home must show a `binary` line without a warning before the install is called done.
- An agent is `agents/<name>/agent.md` in Antigravity's format (`subagent: true`, `mainAgent: false`). Adding a tool to its `tools:` list means adding it to `knownTools` in `internal/harness/inventory.go`: an unknown tool fails the install on purpose, because Antigravity hangs a subagent that names a tool it does not recognise.
- The installer lints every skill, agent, command and rule before it deploys anything (`internal/harness/inventory.go`; each refusal and the bug behind it is in its test, `TestLint*` and `TestAgentDescriptionRules`). It refuses: the flat `agents/<name>.md` format from before ADR-062; a skill without a `SKILL.md` and its `description`; a description over 1,024 characters (the Agent Skills limit), or in an agent one that is not one line or that names "dispatch prompt" or "harness binary"; a frontmatter value a strict YAML parser reads as a comment (Antigravity silently drops such a skill, BUG-004: quote the value); in every kind a frontmatter key outside that kind's allow list (`agentKeys`, `skillKeys`, `commandKeys`, `ruleKeys`; IN23), a permission key (`allowed-tools`, `hooks`, `permissionMode`, `mcpServers`) above all; a command or rule whose file name fails `validName`; and any frontmatter block a YAML reader could read differently from the lint's line grammar (BUG-143, BUG-153). A new key joins a list by hand under a D-row, also for a vendored skill, which is never edited, never a permission key nor a restriction the CLI drops such as `disallowedTools` (ADR-056, ADR-056a): the operator's permission mode decides what runs unprompted.
- Adding a skill, agent, command, or rule is a file drop — never a code change, except a frontmatter key no allow list holds yet. If a new kind of customization needs code, that is a design question, not a quick patch. A new or longer skill description can fail `go test ./...` on the listing budget (`TestSkillListingBudget`, next rule): shorten a description, never raise the number.
- Third-party skills are vendored verbatim and listed in `skills/VENDORED.md`; never edit them in place — fork into a differently named skill. Its second table names the forks: `gke-basics`, which predates this rule and keeps its upstream name, pinned to the base it was rewritten from and never overwritten by a re-fetch, and `discover-skills`, forked from `find-skills` (TS30); `terraform` is the harness's own clean-room skill since 2026-10-01 (D8a). A vendored CATALOG — third-party skills kept as data inside a harness skill, today `skills/google-catalog/catalog/` — is changed only by its refresh script (`bash skills/google-catalog/scripts/refresh-catalog.sh <agents-cli pin> <google-skills pin>`, then `git add skills/google-catalog && go test ./...`): it copies the entries at the pins, refuses what the harness cannot carry until the operator passes `--exclude <entry>`, and regenerates `INDEX.md` and `CHECKSUMS`, which the catalog tests pin both ways; a refresh's diff gets a security review before it is committed; and its entries never become global skills, because the CLI lists only so much (`TestSkillListingBudget` pins the names and descriptions of the skills a model is shown — every skill without `disable-model-invocation: true` — under 19,500 bytes: past Claude Code's budget a skill is a bare name nothing triggers). A pin is written only after `git archive <pin> <path> | tar -x` into scratch and `diff -r` against the directory: the diff is the row's "Local changes", an empty diff is what "verbatim" means, and a pin chosen from a date is a guess (BUG-111; `TestVendoredRowsCarryAPin` refuses a row with no repository or pin, not a wrong one).
- Stdlib only in the Go code, with one exception: `modernc.org/sqlite`, used only by `internal/search` (R4, ADR-045), which also serves `fyr dream`'s read-only reads (R4's dream clause, ADR-047a), by `internal/metrics`, the metrics store (ADR-055), and by `internal/brain`, the brain store (ADR-063). The installer (`internal/harness`) never imports it. Any other dependency is a requirements change.
- `internal/redact/redact.go`'s needles grow by KIND: a vendor's length and alphabet as one regexp, or a prefix only when it is distinctive as written (`sk_test_` sits inside `task_test_`). A review naming a third missed instance on one list gets a rule per kind, not a fourth batch (BUG-110: six passes on 2026-09-30). A needle matched against raw text has no `\b` in front — a literal `\n` or an underscore is a word character and hides the token — and every needle gets a benign near-miss in `TestRedactShapes`; over-redaction in the safe direction is pinned there, never argued about.
- Commit and push after each task, per the global git workflow. This repo is on `main`.

## Testing

There is no test framework beyond `go test`. The procedure is `.agents/docs/testing/guide.md`: § 1 for every change; § 3d for `internal/search` and its wiring (rows in `testing/fyr-matrix.md`); § 3g for `internal/metrics` and its wiring (canary tests, real-data checks from copies only); § 3e for `internal/memory`, `internal/dream` and their wiring, including the reader's corpus measurement (`TestAgyCorpusLeaves`: the leaf count is the box's own corpus, 971 on one box and 197 on another; 0 tool-argument keys is the invariant, held 2026-09-30 and 2026-10-09; re-run when the reader changes); § 2 and § 4 for `context/`, `agents/` and `skills/` (scratch-home install, one sandbox start of the CLI, a behavioural run per changed agent or rule, reported as n of N); § 5 after any real-home install. Every run kit sources `.agents/kit/kit-preamble.sh` first (guide § 4 § Behavioural runs): it asserts the fixture and refuses the setups BUG-087..123 recorded. A change to `context/`, `agents/` or `skills/` gets `/review --docs` over its range; the living docs here include `context/`, `agents/` and every non-vendored skill directory, searched at `skills/` because `.agents/skills` is a symlink.

## Release

Releases are annotated `vX.Y.Z` tags on `main`, cut only by `/preflight vX.Y.Z` (the gate itself — review, security, verification, docs freshness — is `skills/preflight/SKILL.md` Steps 1–5) from the operator's own turn, from this checkout, on any machine logged in to GitHub; no key signs anything (ADR-053). The tag (`git tag -a`, `git` never under `sudo`) is checked before the push — bound first (the tag takes no target and sits on HEAD, the release commit, whose parent is the gated head and whose source tree is the gated one, on `main`), then annotated — with the exact commands in `.agents/docs/deploy/remote.md` § Releases. The tag is the only version tracking (no version file; preflight Step 6.2); a pushed tag is never moved; a bad release gets the next PATCH; a release right after a bridge release waits for the operator's word that every place has crossed it (preflight Step 6, BUG-161). A gate whose "What was not checked" names an Antigravity run of a skill or agent the range changed is NO-SHIP until that run exists: the real-home smoke of `testing/2026-09-03-verify-real-home.md` on Antigravity, plus one run of each changed skill and agent on Antigravity, before the tag (v1.12.0 shipped without them; the operator's rule of 2026-09-29). Catalog entries are data, not changed skills: for them the rule is met by the `google-catalog` router's matrix rows on Antigravity (`catalog-no-leak`, `catalog-route`, `catalog-precedence`) and, when the range refreshes the catalog, by a security review of the refresh's diff — never one run per entry (plan `2026-10-01-google-skills-catalog` D11, D12). What a tag delivers, and to which place, is `.agents/docs/specs/fyr/delivery.md` § The model (rule 6 above).
