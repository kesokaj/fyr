# PRD — fyr

What `fyr` and the harness are for, who they serve, and what must never drift.
Status: current · Owner: the operator · Last updated: 2026-11-14 · Design: [SDD.md](SDD.md) · Technical design: [TDD.md](TDD.md)

> Immutable without the operator's explicit approval. Agents never edit this file.

## Problem

An Antigravity CLI session starts with no memory of the last one and carries only what fits in its 24,000-byte rules block (Known limits). Without a harness, the operator re-explains the stack every session, decisions and past mistakes are lost between conversations, and context copied by hand into each machine's vendor directories drifts from machine to machine.

## Users

- **The operator:** fullstack engineers (Go and TypeScript, or custom stacks via project `AGENTS.md` overrides) working across projects on Linux or macOS (`Apple Silicon`), who decide every architectural choice.
- **The sessions:** the Antigravity CLI and its subagents, which read the context, load the skills and write the trail on the operator's behalf.

## Goals

| # | Goal | Metric | Baseline (2026-10-29) | Target |
|---|---|---|---|---|
| G1 | The context every session carries stays small | hand-written context bytes (`TestRenderedContextUnderTarget`) | 14,876 | ≤ 15,000, always |
| G2 | The project rules every session in this repository reads stay small | `wc -c AGENTS.md` | 21,422 | ≤ 4,500 |
| G3 | The docs agree with the binary | `fyr check` findings on `main` | 2 | 0 at every release |

## Non-goals

- Background daemons, proxies, commit gates, or CI pipelines: the harness is enforced by reading and zero-daemon CLI hooks (`~/.gemini/config/hooks.json` invoking `fyr`, `< 250 ms` fail-open timeout, R3's second exception, ADR-511 superseding ADR-007 in part, ADR-522), never by a long-running process or a commit gate.
- Plugin or marketplace packaging: a namespace would rename every skill and agent.
- Editing any vendor setting (`settings.json`) of a real home: the harness is files in the customization directories (`~/.gemini/config/`, including `hooks.json`, ADR-511), nothing else; the one vendor `settings.json` `fyr` writes is that of an isolated trial/worker or private dream HOME — `fyr eval`'s under `~/.config/fyr/eval/<project>/`, `fyr auto`'s under `~/.config/fyr/sandbox/<project>/` or `~/sandbox/fyr-auto/`, and the dream pass's private home under `~/.config/fyr/dream-agy-home-<pid>/` — never the operator's (ADR-062, ADR-065, ADR-073, ADR-090, ADR-503, ADR-510, ADR-511, ADR-522).
- Symlinking the customization directory to the checkout or a shared store: a copy has no dangling-symlink failure mode, and a release-binary place has no checkout to link to.

- **R0** — Purpose: the second brain of the Antigravity CLI.
  <!-- provenance: the operator, 2026-10-24; enforced by: TestHarnessMap, TestAddGetEditList, TestSearchRanksARecordAboveAFile, TestMemoryVerb, TestRunIngestsMetricsFirst, TestRenderedContextUnderTarget, TestWorkerModelRunCountAndCap, TestMemoryPartsAndGlobalScope, TestComputeMemoryValidity, TestDreamingOnlyClassSet, TestPreInvocationProgressiveMemory, TestEvalGate -->

  `fyr` is the second brain and build controller of the Antigravity CLI, with two jobs and no custom interactive worker runner (parallel and delegated interactive work runs on Antigravity's own `invoke_subagent`, `run_workflow` and `swarm` dispatchers). First, it controls builds and holds what a session cannot hold on its own: the context, skills, rules, agents and zero-daemon CLI hooks (`install`); every record of every project's trail and its project memory in one searchable store (`record`, `search`, `memory`); the shape and usage reports of every session (`metrics`, `report`); live model routing (`models`); and deterministic verification, write-lease gating, branch landing, session closing and drift checks (`check` and the build-control verbs), while keeping the hand-written context under its size pin. The CLI consults it at session start, before touching or reading an area, when routing subagents or workflows, at turn end and phase close, and through its `< 250 ms` fail-open CLI hooks (`~/.gemini/config/hooks.json`, R3, ADR-511, ADR-522). Second, when turned on, `fyr auto` (R3) improves skills and memory through dreaming: it ingests telemetry, runs idle-project dream consolidation (`dream`), and turns trajectory and conversation telemetry into `eval`-gated `skills/` edits or new distilled skills in the harness checkout, quarantined skill proposals, and derived validity-scored memory cards — conversations of their own that no interactive CLI session is sent into. No background daemon or proxy acts on a CLI session. (ADR-061, ADR-062, ADR-063, ADR-073, ADR-090, ADR-511, ADR-522, ADR-523.)

- **R1** — One source, one vendor.

- **R2** — Standards, not vendor formats.

  The context follows the agents.md standard and is named `AGENTS.md` at every level; a project has `AGENTS.md` at its root and no vendor-named copy of it. A template `AGENTS.md` never sits beside source. Skills follow the Agent Skills `SKILL.md` standard so that anything from skills.sh or any other source drops into `skills/` unchanged.

- **R3** — No daemons, no gates, no CI; two exceptions.
  <!-- provenance: the operator, 2026-09-03; enforced by: TestStoreRunsNoProjectHook, TestHookHardDeadlineFallsBackToAllow, TestUnrangedReadOf600LineFileDeniedWithSkeletonAndRangedRetryAllowed, TestReadLedgerPersistenceEditAndExternalCheckout, TestVerifyHappyAndMustFail, TestGateChecksAndMustFail, TestInstallTimerLinux, TestDreamTimerDryRun, TestPromptCarriesMetricsNumbersOnly, TestAutoOnWritesTheConfigAndTheTimer, TestAutoOffNeedsNoLock, TestAutoOffReplacesCorruptAndLink, TestAutoRunOffIsOneLine, TestAutoRunCorruptFailsClosed, TestAutoConfigCorrupt, TestAutoTimerSystemdText, TestAutoTimerPlistText, TestGateRereadBeforeEachProject, TestGateMachineStopsARun, TestGateUnknownPresenceIsLogged, TestGateCleanStops, TestGateIdleEachClock, TestUsageFloors, TestUsageRefusals, TestAutoRunHeldLockStops, TestReportStaysOutOfTheProject, TestWorkerModelRunCountAndCap, TestWorkerConfigTamperDisablesAuto, TestWorkerStateTamperRestoredAndDraftsCollected, TestApplyHappyPath, TestApplyMovedCheckoutKeepsBranch, TestApplyRedMarkedTestKeepsBranch, TestApplyNoMarkedTestBecomesProposal, TestApplyHooksAndGPGSignOff, TestApplyNoPushFetchOrLsRemoteInGitLog, TestApplyRubricDeniedPathOnBranchKeepsBranch, TestApplyStep1RereadsGatesAndDraftFindings, TestProvenanceMigrationSetsUnknown, TestProvenanceMemoryAdd, TestProvenanceMemoryDraftActions, TestProvenanceFeedbackAndRecordAdd, TestMemoryProvenanceFlag, TestDraftsMemoryAddRetireMerge, TestDraftsRetireOrMergeOtherProjectRefused, TestDraftsTokenShapeRefused, TestDraftsFeedbackProposalFindingAndLimits, TestEvalGate -->

  The harness is context, skills, and subagents. Behaviour comes from what is written in them, not from background daemons, proxies, commit gates, or pipelines. Git is backup and versioning only. Two exceptions. The first: `fyr auto`, the single background runner, invoked hourly by an OS user timer that `fyr auto on` installs and `fyr auto off` or `uninstall` removes (with the former standalone dream timer merged into `fyr auto`). It does nothing unless `~/.config/fyr/auto.json` says it is on (missing or corrupt counts as off), which `fyr` writes only in `on` and `off`; `off` needs no lock. Each run first ingests Antigravity CLI conversations into the metrics store (R4). For its dream consolidation pass (also runnable explicitly via `fyr dream`), over projects registered with `fyr index --register` (a marker inside the checkout's `.git/`, which no clone carries) that are idle for at least a day and have something new since their last dream, it reads those projects' records and memory, global feedback records, Antigravity CLI conversations, and a numbers-only summary of the metrics store (metric keys and values for each project's window and the window before, never a tool, skill, agent, label or path) through the redactor first, and runs the CLI headless in plan mode with no tool granted: in the operator's own Antigravity home from an empty directory under `~/.config/fyr/` when that home's settings grant no tool without review (so each project's dream is visible in `/resume`), and otherwise in a private home under `~/.config/fyr/dream-agy-home-<pid>/` that grants none, never with `--dangerously-skip-permissions`. Dream writes stay under `~/.config/fyr/` as global `proposal` records (plus the CLI's own `brain/` conversation and plan file, discarded when private, ADR-089) and never edit a project, skill, rule or the context directly. For its maintenance and self-improvement sweep, before each project `fyr auto` reads `auto.json` again and requires AC power, no sign of the operator at the machine (an unknown reading does not stop it, and is logged) and no interactive Antigravity CLI session of the operator's. One run goes at a time over registered, migrated projects idle for at least its threshold (six hours by default), clean, on a branch that has an upstream and is not ahead of it. A model task also needs quota: no pool under half of its 5-hour window or 30 % of its week remaining, an unreadable reading counting as under. At level `observe`, the default, it runs free checks, spends no model and changes no project. At most four model tasks run a day, 30 minutes each; a worker already running is not stopped by gate re-reads, and if a worker tampers with `auto.json`, a post-session tripwire resets it to off. At level `project` or `harness`, an isolated dreaming worker (R6, R8, R10) handles only existing skills, new distilled skills, quarantined skill-search asks, and derived memory cards — never editing consumer project code or docs: in the harness checkout, a skill edit or new distilled skill under `skills/` runs on a local `work/auto-*` branch and `fyr` itself, never the model, squashes and fast-forwards it — one commit `git revert` undoes — only after `# auto: test` marked tests pass, `fyr check` passes where `PRD.md` exists, and the isolated eval gate passes (R9, one model task capped at 24 eval sessions under `~/sandbox/fyr-auto/` outside every checkout); consumer-repo distilled skills and missing-skill searches stay a kept branch, a kept sandbox, or a quarantined `proposal` record. `fyr` re-reads the switch before each apply and never pushes, installs a third-party skill, MCP server or dependency, or lands what the rubric denies, including `PRD.md`, every `AGENTS.md`, `context/`, `rules/`, `agents/` and every Go test and test fixture. Its config, state and reports live under `~/.config/fyr/` and in the global store; derived memory and feedback are validated by `fyr`, deterministically scored in Go, and marked `derived`, becoming a rule only on the operator's word and a skill only on that word or, in the harness checkout, the eval gate (R9). (ADR-047a, ADR-062, ADR-068, ADR-073, ADR-089, ADR-089a, ADR-090, ADR-522, ADR-523.) The second: zero-daemon Antigravity CLI hooks in `~/.gemini/config/hooks.json` across up to five lifecycle events (`SessionStart`, `PreInvocation`, `PreToolUse`, `PostToolUse`, `Stop`), deployed by `fyr install` and invoking `fyr` as a one-shot command under a `< 250 ms` fail-open budget with a hard internal deadline (~200 ms, falling back to `allow` / exit 0 on timeout or internal error, emitting a 1-line `user_markdown` degradation banner when a store is unavailable, never running `go`, `git` or the network, and bypassable globally via `~/.config/fyr/no-hooks` or per checkout via `.agents/scratch/no-hooks`). They emit a compact `SessionStart` capsule, inject Turn-0 structural symbol/heading capsules and re-prime state after compaction on `PreInvocation`, enforce a skeleton-first clamp on large unranged file reads (denying once with a skeleton, allowing ranged retries, never rewriting read arguments via `overwrite`), deduplicate unchanged reads in a persistent content-hash-keyed ledger (surviving blocked reads and invalidated only by a content-hash change or overlapping edit), route `invoke_subagent`, `swarm` and `run_workflow` models with quota fallback and record passive co-activity on `PreToolUse`, reserve `PostToolUse` under the same read-only `< 250 ms` contract, and perform a stamp-only verification nudge on `Stop` (returning `continue` once when Go files changed in the turn and no green verification stamp matches the current tree hash, comparing stamps only and never running tests). (ADR-511, ADR-520, ADR-521, ADR-522.)

- **R4** — One binary, one dependency, easy on and off.
  <!-- provenance: the operator, 2026-09-29; enforced by: go.mod, TestInstallStatusResyncUninstall, TestUninstallKeepsMetricsStore, TestUpdateNeverInstallsDirtyTree, TestUninstallRemovesAutoTimerKeepsItsFiles -->

  `fyr` is a single Go binary. Its one dependency is `modernc.org/sqlite`, a pure-Go SQLite driver used only by the search index, the metrics store and the brain store, pinned in `go.mod` and `go.sum` and not vendored; `fyr dream` also opens Antigravity's conversation databases with it, read-only; filesystem isolation for `fyr eval` and `fyr auto` uses Go's stdlib `syscall` package (Linux Landlock syscalls 444–446) and macOS `sandbox-exec` with no new dependency; any other dependency, and any driver that needs cgo, is a requirements change. The search indexes (`.agents/scratch/search.db` in a project, `~/.config/fyr/search.db`) are caches derived from files git or `~/.config/fyr/` already holds (including the pure-Go AST and Markdown heading symbol/reference graph, persistent content-hash read ledger, and passive co-activity in `.agents/scratch/search.db`, ADR-511, ADR-522): never committed, rebuilt when deleted. The metrics store (`~/.config/fyr/metrics.db`) is not a cache: it holds the shape of every ingested session (tools, normalised command verbs, salted file-read hashes, tokens, timings, never arguments or prose, and no raw path but each session's project root and the transcript files it read), including the Claude Code sessions ingested before ADR-062, kept as history, and is the only copy once a transcript expires, so it is migrated forward and never rebuilt or deleted by the binary, never committed, and `uninstall` leaves it. The brain store (`~/.config/fyr/brain.db`) is a store of record like the metrics store: every project record and every memory, feedback and proposal record lives in the store (`uninstall` leaves it), while `fyr record export` writes a project's trail records to `.agents/trail.jsonl` on demand and `fyr record sync` loads `.agents/trail.jsonl` back into the store and its FTS index when moving data between machines. `install` is idempotent and overwrites only files it manages; `uninstall` removes exactly what its manifest lists and `fyr auto`'s timer (plus any legacy dream timer) when installed (R3), leaving `fyr auto`'s config and state; `update` pulls the repo from git and reinstalls. `update` refuses a checkout with uncommitted changes on every path, because it deploys the working tree rather than the commit it fetched; `install` stays the deliberate way to deploy a dirty tree. `install` writes no vendor `settings.json` (Non-goals). (ADR-045, ADR-047a, ADR-062, ADR-091, ADR-511, ADR-522.)

- **R5** — Hand-added customizations are first class.
  <!-- provenance: the operator, 2026-09-03; enforced by: TestInstallStatusResyncUninstall, TestAdopt, TestLintAllowListPerKind -->

  Adding a skill, subagent, command, or rule is: put the file in `skills/`, `agents/`, `commands/`, or `rules/` (by hand, by `npx skills add` from the repo root, or by `fyr adopt`), then `fyr install`. No registration, no manifest edits, no code. The installer maps each directory to its place under `~/.gemini/config/`.

- **R6** — Development never touches the real home.
  <!-- provenance: the operator, 2026-09-03; enforced by: TestEvalRefusesWithoutHome, TestEvalRefusesItsHome, AGENTS.md -->

  Every test and every development run of the installer or a state-writing verb uses `--home` with a scratch directory (or a dedicated non-checkout home for `fyr eval`). `fyr eval` refuses to run without an explicit `--home` outside the operator's real `$HOME` and outside every git checkout, and confines every trial's filesystem writes to its scratch home and workspace under OS-level isolation (`isolate`: Linux Landlock and macOS `sandbox-exec`, refusing to run if OS isolation is unavailable rather than running unconfined on the host), so writes outside the scratch home fail with `EACCES` and the real `$HOME` is untouched. Deploying to the operator's real `$HOME` is the operator's action, except on a machine whose `DEPLOY-local` record § Operator steps records the operator's standing permission to keep it current: there a session's checkpoint ends with `fyr install` from a clean, pushed checkout into the real home. (ADR-078, ADR-505, ADR-522.)

- **R7** — Projects remember and stay resumable.
  <!-- provenance: the operator, 2026-09-03; enforced by: TestAddGetEditList, TestExportByteStable, TestLoadReplacesRowsFromAChangedFile, TestEveryUnexportedKindStaysOut, TestStateDirHasOneHome, TestReportStaysOutOfTheProject -->

  Every project keeps its scratch in `.agents/scratch/` (gitignored), its root docs (`AGENTS.md`, `PRD.md`, `SDD.md`, `TDD.md`, `TODO.md`) in the checkout so work can continue with or without `fyr`, and its trail as records in the brain store (`~/.config/fyr/brain.db`): plans with task checkboxes, reviews, test logs, changes, handoffs, numbered bugs, ADRs, retros, learnings, specs, deploy and testing guides. Records in `brain.db` (and rows in `metrics.db`) are never deleted by `fyr`: closing a task or phase writes one handoff record embedding the verification digest rather than separate per-task `change` and `testing` records, while every existing `change`, `testing` and other trail record remains permanently in the store. Records are written and read through `fyr record` and searched with `fyr search` directly in the brain store without writing to the checkout; when the operator wants to move or snapshot a project's trail, `fyr record export` writes `.agents/trail.jsonl` and `fyr record sync` loads it into the store on the target machine. Its memory is `semantic`, `procedural`, and `episodic` `memory` records in the same store (project-scoped or shared via `--global`), deterministically validity-scored in Go (hiding cards below `0.40`), local to the machine and never exported. The harness's own state (manifest, the brain store, the global search index, the metrics store) lives in `~/.config/fyr/` and nowhere else. `fyr auto`'s reports stay on the machine (R3). (ADR-015, ADR-063, ADR-091, ADR-522, ADR-523.)

- **R8** — One delivery channel, and it is `fyr`.
  <!-- provenance: the operator, 2026-09-17; enforced by: TestHarnessMap, TestGlobalOnlyKinds, TestEveryUnexportedKindStaysOut, TestUpdateFromZipVerifiedAndTampered, TestDeliverySpecCurrent, TestKickoffBuilder, TestKickoffRubricAndAsks, TestRunnerChoice, TestWorkerBranchCleanup, TestIsolateLandlockDeniesOutsideWrite, TestSeatbeltProfileRender, TestTasksKickoffTemplates, TestTasksTriggers, TestTasksRedactedLearningInput, TestMemoryPartsAndGlobalScope, TestComputeMemoryValidity, TestDreamingOnlyClassSet, TestPreInvocationProgressiveMemory, TestEvalGate -->

  The harness reaches a machine one of three ways: a checkout the operator owns; a release's `fyr` binary with the harness built in; or a zip of the repository that the operator downloads and passes to `fyr update --from-zip <file>`. Each is kept current with `fyr update`: the checkout and the binary as today, and a zip place by the operator repeating the download and `--from-zip`. There is no other channel — no vendored mirror inside a consumer project, no per-project copy, no service. A project that wants the harness uses `fyr`; this repository names no consumer project and depends on none. Nothing flows back: no verb but those named here sends the machine's corrections, proposals, memory or metrics anywhere; `feedback` and `proposal` records are global only, `memory` records are never exported, and `fyr record` refuses the first two in a project, and four things are sent by design: to the model of the CLI the machine already uses: the dreamer's redacted prompt (R3), and the isolated runs of `fyr eval` (started by the operator's session or by `fyr auto`) and `fyr auto`'s workers when turned on (R3), which send a sandboxed clone's prompts and the files its agent reads, unredacted, as any session of that CLI does, and, for `fyr auto`'s dreaming tasks, the conversations, memory, proposals, and trajectory/metric digests `fyr` gives a worker, through the dream's redactor first; and to skills.sh and the npm registry, the search of a `fyr auto` worker looking for a missing skill, its query words unredacted. The runner list for `fyr eval` and `fyr auto` workers is `isolate` (the default once Phase 5's dual-run gate passes: OS filesystem confinement via stdlib `syscall` Landlock on Linux and `sandbox-exec` on macOS, refusing to run when OS isolation is unavailable rather than falling back to an unconfined host run; Docker remains a transitional runner option only until Phase 6b removes the container and worker packages). Scope checks and `auto.json`'s watch remain tripwires alongside OS filesystem confinement, while a worker's agent still has `command(*)` inside its confined paths and network access, so outbound network traffic is governed by design as above (ADR-065, ADR-090, ADR-522). Experience reaches the harness only through the operator's own hands in their checkout, or an eval-gated `fyr auto` commit to that checkout's local branch (R9), which those hands push. (ADR-030, ADR-033, ADR-038, ADR-062, ADR-090, ADR-515, ADR-522, ADR-523.)

- **R9** — Three procedures, set in stone.
  <!-- provenance: the operator, 2026-10-24; enforced by: TestHarnessMap, TestUpdateNeverInstallsDirtyTree, TestUpdateFromReleaseReplacesAndInstalls, TestUpdateFromZipVerifiedAndTampered, skills/fyr-preflight/SKILL.md, TestEvalGate -->

  The harness is operated by three procedures and no others, drawn in `README.md` § How it works:

  - **Install:** a place either clones `fyr` (HTTPS or SSH) and runs `fyr install`, or downloads a release's `fyr` binary — `curl` / browser from the Releases page, `gh release download`, or `go install` — and runs `fyr install`, which installs the harness built into the binary. Either way installed files go into `~/.gemini/config/` and no repository is created.
  - **Update:** the operator edits, verifies, commits and pushes `main` in their checkout, or `fyr auto` commits an eval-gated skill edit or distilled skill under `skills/` to the checkout's local branch, which the operator pushes. A checkout place runs `fyr update` when the operator decides — fetch, refuse a dirty checkout, fast-forward, rebuild, reinstall. A binary-only place runs `fyr update`, which downloads the newest release, checks it against the release's `SHA256SUMS`: integrity, not authenticity — trust rests on GitHub's HTTPS release channel and the maintainer's GitHub account, as for a checkout place — replaces the binary and reinstalls; it changes only when a release is cut. Nothing is pushed to a machine.
    - **Zip place:** the operator downloads the repository zip by hand and runs `fyr update --from-zip <file>`. It unpacks the zip into a temporary directory, refuses any entry that would leave it, installs that tree with the running binary, and deletes the directory. Nothing is fetched, no repository is created, and nothing in the zip replaces the binary. When the release's `SHA256SUMS` sits beside the zip, the zip is checked against it and refused on a mismatch; a zip without it is installed marked `UNVERIFIED`.
  - **Release:** `/fyr-preflight vX.Y.Z`, from the operator's own turn, gates the tree through parallel preflight (`run_workflow` parallel code and security review, deterministic verification, and isolated changed-row `fyr eval` runs), pushes an annotated tag on `main`, and publishes that tag's binaries and a zip of its tree (`git archive`), with their `SHA256SUMS`; no key is needed, so any machine with the maintainer's GitHub write credential can cut one. Checkout places follow `main`; binary-only places update to the newest release.

  The three procedures and the map change together, only with the operator's explicit approval, an ADR, and one commit carrying the code, the docs and the map. (ADR-031, ADR-033, ADR-038, ADR-039, ADR-040, ADR-041, ADR-053, ADR-062, ADR-090, ADR-515, ADR-522, ADR-523; each quotes the operator's approval of its text.)

- **R10** — One behaviour on every place.
  <!-- provenance: the operator, 2026-10-24; enforced by: TestTimerMacOS, TestAgySessionMac, TestAgySessionLinux, TEST-2026-09-04-verify-mac-real-home, TestRunnerChoice, TestAutoOnWritesTheConfigAndTheTimer, TestAutoTimerPlistText, TestIsolateLandlockDeniesOutsideWrite, TestSeatbeltProfileRender -->

  Every harness feature is set up and runs the same at every place, whichever of the three ways in (R8) it came by, and on every operating system the operator runs it on (Linux, macOS). Filesystem isolation for `fyr eval` and `fyr auto` provides the same confinement contract on both platforms — stdlib `syscall` Landlock on Linux and `sandbox-exec` on macOS — refusing to run when the platform's isolation primitive is unavailable rather than running unconfined on the host (R6, R8); `fyr auto`'s level `harness` needs a checkout, so it runs only at checkout places (R3, R8, ADR-090). What only the Antigravity CLI's own runtime or the host OS controls, and neither the context nor `fyr` can reach, is a Known limit below. (ADR-047, ADR-062, ADR-090, ADR-522.)

## Known limits

- **Antigravity global rules are one 24,000-byte block.** CLI 1.2.7 builds one block from `~/.gemini/config/rules/*.md` and cuts it at 24,000 bytes with a `<truncated N bytes>` marker; a second file costs the first one room, and what falls past the cut is dropped without a marker (BUG-085, measured 2026-09-21); files that fit under the cut all load (measured 2026-10-05: context and `critical-thinking.md`, 16,993 bytes; ADR-051; the vendor page, read 2026-09-30, now says 24,000 bytes per file plus a 20,000-token budget across all always-on rules, so the discrepancy with the measured single block stands as measured). The deployed context is pinned under 22,000 bytes by a test, and `rules/` files share the block.
- **Antigravity global rules path.** The CLI's customization root is `~/.gemini/config/`; rules there are documented for the workspace form (`.agents/rules/*.md`) and by analogy for the global one. Verified on the Linux box 2026-09-03 (`TEST-2026-09-03-verify-real-home` (`fyr record get`)): the CLI reads rules, skills, and agents from there. Confirmed on the Mac for Antigravity on 2026-09-04 (`TEST-2026-09-04-verify-mac-real-home`).
- **Antigravity tool names cannot be enumerated.** An unrecognised name in an agent's `tools:` hangs the subagent, so `fyr install` fails on any tool name it does not know rather than guessing.
- **Antigravity IDE is out of scope.** Only the `agy` CLI is targeted; the IDE's global paths are unverified.
- **`agy --sandbox` scope and OS isolation prerequisites (Linux Landlock, macOS `sandbox-exec`).** `agy --sandbox` restricts terminal commands only and does not confine built-in file tools (`agy --help`), so `fyr eval` and `fyr auto` enforce process-wide filesystem isolation via Linux Landlock (kernel 5.13+, syscalls 444–446) and macOS `sandbox-exec` (Apple-deprecated at the API level, still shipped in macOS). There is no Docker runner or unconfined `--runner auto` host fallback after the v9 migration: a machine whose kernel lacks Landlock or whose macOS lacks `sandbox-exec` refuses `fyr eval` and `fyr auto` worker runs closed rather than running unconfined on the host (ADR-522, superseding ADR-504, ADR-507 and ADR-510's host fallback).
- **Antigravity has no compaction window a file can set.** A session compacts when the CLI decides; the session-sizing rule (`rules/session-sizing.md`, ADR-058) is the only mechanism that ends a session at its checkpoint.
