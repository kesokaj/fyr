# PRD — fyr

What `fyr` and the harness are for, who they serve, and what must never drift.
Status: current · Owner: the operator · Last updated: 2026-11-08 · Design: [SDD.md](SDD.md) · Technical design: [TDD.md](TDD.md)

> Immutable without the operator's explicit approval. Agents never edit this file.

## Problem

An Antigravity CLI session starts with no memory of the last one and carries only what fits in its 24,000-byte rules block (Known limits). Without a harness, the operator re-explains the stack every session, decisions and past mistakes are lost between conversations, and context copied by hand into each machine's vendor directories drifts from machine to machine.

## Users

- **The operator:** one fullstack engineer (Go and TypeScript) who works across several projects on a Linux box and a Mac, and decides every architectural choice.
- **The sessions:** the Antigravity CLI and its subagents, which read the context, load the skills and write the trail on the operator's behalf.

## Goals

| # | Goal | Metric | Baseline (2026-10-29) | Target |
|---|---|---|---|---|
| G1 | The context every session carries stays small | hand-written context bytes (`TestRenderedContextUnderTarget`) | 14,876 | ≤ 15,000, always |
| G2 | The project rules every session in this repository reads stay small | `wc -c AGENTS.md` | 21,422 | ≤ 12,000 |
| G3 | The docs agree with the binary | `fyr check` findings on `main` | 2 | 0 at every release |

## Non-goals

- Background daemons, proxies, commit gates, or CI pipelines: the harness is enforced by reading and zero-daemon CLI hooks (`~/.gemini/config/hooks.json` invoking `fyr`, `< 250 ms` fail-open timeout, R3's third exception, ADR-511 superseding ADR-007 in part), never by a long-running process or a commit gate.
- Plugin or marketplace packaging: a namespace would rename every skill and agent.
- Editing any vendor setting (`settings.json`) of a real home: the harness is files in the customization directories (`~/.gemini/config/`, including `hooks.json`, ADR-511), nothing else; the one vendor `settings.json` `fyr` writes is that of a sandbox or private dream HOME — `fyr eval`'s under `~/.config/fyr/eval/<project>/`, `fyr work`'s under `~/.config/fyr/sandbox/<project>/`, and `fyr dream`'s private home under `~/.config/fyr/dream-agy-home-<pid>/` — never the operator's (ADR-062, ADR-065, ADR-073, ADR-076, ADR-503, ADR-510, ADR-511).
- Symlinking the customization directory to the checkout or a shared store: a copy has no dangling-symlink failure mode, and a release-binary place has no checkout to link to.

- **R0** — Purpose: the second brain of the Antigravity CLI.
  <!-- provenance: the operator, 2026-10-24; enforced by: TestHarnessMap, TestAddGetEditList, TestSearchRanksARecordAboveAFile, TestMemoryVerb, TestRunIngestsMetricsFirst, TestRenderedContextUnderTarget, TestWorkerModelRunCountAndCap, TestEvalRerunTriggers, TestEvalGate -->

  `fyr` is the second brain of the Antigravity CLI. It keeps what a session cannot hold on its own: the context, skills, rules, agents and zero-daemon CLI hooks (`install`); every record of every project's trail, with its metadata, in one store the CLI searches when it needs to (`record`, `search`), and the project memory in the same store (`memory`); the shape of every session (`metrics`); and the consolidation of idle projects (`dream`). The CLI asks it for help at the moments the context names — resume, before touching an area, at a phase end, when a skill or context seems missing, and when work starts drifting — and through its `< 250 ms` fail-open CLI hooks (`~/.gemini/config/hooks.json`, R3, ADR-511). It grows to evaluate projects and catch drift in the binary and its specs, never in the context, whose hand-written part stays under its size pin. No background daemon or proxy acts on a CLI session: the conversations `fyr` starts unasked are the visible dream (R3), a conversation of its own that no session is sent into, and, while the operator has turned it on, `fyr auto`'s workers and eval runs in their own sandboxes (R3), which no session is sent into either. (ADR-061, ADR-062, ADR-063, ADR-073, ADR-090, ADR-511.)

- **R1** — One source, one vendor.
  <!-- provenance: the operator, 2026-10-24; enforced by: TestAgentsInstallAsWritten, TestRenderedContextFitsAntigravityBlock, TestEmbedHoldsOnlyTrackedFiles -->

  `context/AGENTS.md` (plus `context/*.md`) is the single global context, deployed to the Antigravity CLI and to no other CLI. Subagents are authored in Antigravity's format as `agents/<name>/agent.md` and installed unchanged; nothing is derived, and nothing generated is committed. (ADR-062.)

- **R2** — Standards, not vendor formats.
  <!-- provenance: the operator, 2026-09-03; enforced by: TestInitProjectRootDocs, TestSkillDirWithoutSkillMdIsSkipped, TestLintAllowListPerKind -->

  The context follows the agents.md standard and is named `AGENTS.md` at every level; a project has `AGENTS.md` at its root and no vendor-named copy of it. A template `AGENTS.md` never sits beside source. Skills follow the Agent Skills `SKILL.md` standard so that anything from skills.sh or any other source drops into `skills/` unchanged.

- **R3** — No daemons, no gates, no CI; three exceptions.
  <!-- provenance: the operator, 2026-09-03; enforced by: TestStoreRunsNoProjectHook, TestRunLeadHooksOff, TestInstallTimerLinux, TestDreamTimerDryRun, TestPromptCarriesMetricsNumbersOnly, TestAutoOnWritesTheConfigAndTheTimer, TestAutoOffNeedsNoLock, TestAutoOffReplacesCorruptAndLink, TestAutoRunOffIsOneLine, TestAutoRunCorruptFailsClosed, TestAutoConfigCorrupt, TestAutoTimerSystemdText, TestAutoTimerPlistText, TestGateRereadBeforeEachProject, TestGateMachineStopsARun, TestGateUnknownPresenceIsLogged, TestGateCleanStops, TestGateIdleEachClock, TestUsageFloors, TestUsageRefusals, TestAutoRunHeldLockStops, TestReportStaysOutOfTheProject, TestWorkerModelRunCountAndCap, TestWorkerConfigTamperDisablesAuto, TestWorkerStateTamperRestoredAndDraftsCollected, TestApplyHappyPath, TestApplyMovedCheckoutKeepsBranch, TestApplyRedMarkedTestKeepsBranch, TestApplyNoMarkedTestBecomesProposal, TestApplyHooksAndGPGSignOff, TestApplyNoPushFetchOrLsRemoteInGitLog, TestApplyRubricDeniedPathOnBranchKeepsBranch, TestApplyStep1RereadsGatesAndDraftFindings, TestProvenanceMigrationSetsUnknown, TestProvenanceMemoryAdd, TestProvenanceMemoryDraftActions, TestProvenanceFeedbackAndRecordAdd, TestMemoryProvenanceFlag, TestDraftsMemoryAddRetireMerge, TestDraftsRetireOrMergeOtherProjectRefused, TestDraftsTokenShapeRefused, TestDraftsFeedbackProposalFindingAndLimits, TestEvalGate -->

  The harness is context, skills, and subagents. Behaviour comes from what is written in them, not from background daemons, proxies, commit gates, or pipelines. Git is backup and versioning only. Three exceptions. The first: `fyr dream --all`, run hourly by an OS user timer that `fyr dream --install-timer` installs and `fyr dream --remove-timer` or `uninstall` removes, acts only while an Antigravity CLI process of the operator's runs (a process check when the timer fires, no daemon), over the projects the operator registered with `fyr index --register` (a marker inside the checkout's `.git/`, which no clone carries) that are idle for at least a day and have something new since their last dream. It reads those projects' records and memory and the global feedback records and the Antigravity CLI's conversations, and a numbers-only summary of the metrics store (its metric keys and values for each project's window and the window before, never a tool, skill, agent, label or path), first ingests those conversations into the metrics store (R4), and runs the CLI headless in plan mode with no tool granted over what it read (plan mode still writes its own plan file in the CLI's `brain/` directory, and such a turn gives no answer): in the operator's own Antigravity home, from an empty working directory under `~/.config/fyr/`, when that home's settings grant no tool without review, so each project's dream is one conversation the operator can open with `/resume`, and otherwise in a private home that grants none, never with `--dangerously-skip-permissions`. A dream run's own writes stay under `~/.config/fyr/`, its proposals as global `proposal` records. The CLI writes its conversation and that plan file in its own store: in the operator's Antigravity home on the visible branch, where they stay, and in the private home otherwise, which goes when the run ends. That a plan-mode write cannot land elsewhere is not shown (ADR-089). The dream's own code never edits a project, a skill, a rule or the context, and a proposal takes effect only through `/retro`. (ADR-047a, ADR-062, ADR-068, ADR-073, ADR-089, ADR-089a.) The second: `fyr auto run`, hourly by an OS user timer that `fyr auto on` installs and `fyr auto off` or `uninstall` removes. It does nothing unless `~/.config/fyr/auto.json` says it is on (missing or corrupt counts as off), which `fyr` writes only in `on` and `off`; `off` needs no lock. Before each project it reads the switch again and requires AC power, no sign of the operator at the machine (an unknown reading does not stop it, and is logged) and no interactive Antigravity CLI session of the operator's found by the dream's process check, which can miss one. One run goes at a time, over registered, migrated projects idle for at least its threshold (six hours by default), clean, on a branch that has an upstream and is not ahead of it. A model task also needs its quota: no pool with under half of its 5-hour window or 30 % of its week remaining, an unreadable reading counting as under. At level `observe`, the default, it runs free checks, spends no model and changes no project. A worker already running is not stopped by any of these. At most four model tasks run a day, 30 minutes each. A worker can still change `auto.json`; a tripwire catches that only after its session, and `fyr` then writes it to turn auto off. At level `project`, or level `harness` for a `harness-edit`, a worker in a sandbox clone makes a `work/auto-*` branch, and `fyr` itself, never the model, squashes a change the risk rubric allows onto the project's local branch and fast-forwards it, one commit that `git revert` undoes, only after the project's marked tests pass, and `fyr check` too where the project has a `PRD.md`, and, for a `harness-edit`, the eval gate (R9); anything else stays a kept branch, a kept sandbox or a `proposal` record. It reads the switch again before each apply. `fyr` itself never pushes, installs a third-party skill, MCP server or dependency, or lands what the rubric denies, which includes `PRD.md`, every `AGENTS.md`, `context/`, `rules/` and every Go test and test fixture. On the host runner that binds `fyr`, not the model; only tripwires watch the model there (R8). Its config, state and reports live under `~/.config/fyr/` and in the global store. Memory and feedback it derives, and the memory records it retires or merges in a project, are validated by `fyr`; what it adds is marked `derived` and becomes a rule only on the operator's word, and a skill only on that word or, at level `harness`, the eval gate (R9). An eval gate counts as one model task and stops at 24 eval sessions; its home and held-out rows live under `~/sandbox/fyr-auto/`, outside every checkout. (ADR-090.) The third: zero-daemon Antigravity CLI hooks in `~/.gemini/config/hooks.json` (`PreInvocation`, `PreToolUse`, `Stop`), deployed by `fyr install` and invoking `fyr` as a one-shot command with `< 250 ms` fail-open timeout (exit 0 on any internal error, emitting a 1-line `user_markdown` degradation banner when a store is unavailable) to inject Turn-0 structural symbol capsules, re-prime memory and ready plan phases after context compaction, deduplicate redundant unchanged file reads on a consume-on-hit session ledger, and record passive co-activity — with zero background daemons or proxies. (ADR-511.)

- **R4** — One binary, one dependency, easy on and off.
  <!-- provenance: the operator, 2026-09-29; enforced by: go.mod, TestInstallStatusResyncUninstall, TestUninstallKeepsMetricsStore, TestUpdateNeverInstallsDirtyTree, TestUninstallRemovesAutoTimerKeepsItsFiles -->

  `fyr` is a single Go binary. Its one dependency is `modernc.org/sqlite`, a pure-Go SQLite driver used only by the search index, the metrics store and the brain store, pinned in `go.mod` and `go.sum` and not vendored; `fyr dream` also opens Antigravity's conversation databases with it, read-only; any other dependency, and any driver that needs cgo, is a requirements change. The search indexes (`.agents/scratch/search.db` in a project, `~/.config/fyr/search.db`) are caches derived from files git or `~/.config/fyr/` already holds (including the pure-Go AST symbol and reference graph, session read ledger, and passive co-activity in `.agents/scratch/search.db`, ADR-511): never committed, rebuilt when deleted. The metrics store (`~/.config/fyr/metrics.db`) is not a cache: it holds the shape of every ingested session (tools, normalised command verbs, salted file-read hashes, tokens, timings, never arguments or prose, and no raw path but each session's project root and the transcript files it read), including the Claude Code sessions ingested before ADR-062, kept as history, and is the only copy once a transcript expires, so it is migrated forward and never rebuilt or deleted by the binary, never committed, and `uninstall` leaves it. The brain store (`~/.config/fyr/brain.db`) is a store of record like the metrics store: every project record and every memory, feedback and proposal record lives in the store (`uninstall` leaves it), while `fyr record export` writes a project's trail records to `.agents/trail.jsonl` on demand and `fyr record sync` loads `.agents/trail.jsonl` back into the store and its FTS index when moving data between machines. `install` is idempotent and overwrites only files it manages; `uninstall` removes exactly what its manifest lists, and the dream timer and `fyr auto`'s timer when installed (R3), leaving `fyr auto`'s config and state; `update` pulls the repo from git and reinstalls. `update` refuses a checkout with uncommitted changes on every path, because it deploys the working tree rather than the commit it fetched; `install` stays the deliberate way to deploy a dirty tree. `install` writes no vendor `settings.json` (Non-goals). (ADR-045, ADR-047a, ADR-062, ADR-091, ADR-511.)

- **R5** — Hand-added customizations are first class.
  <!-- provenance: the operator, 2026-09-03; enforced by: TestInstallStatusResyncUninstall, TestAdopt, TestLintAllowListPerKind -->

  Adding a skill, subagent, command, or rule is: put the file in `skills/`, `agents/`, `commands/`, or `rules/` (by hand, by `npx skills add` from the repo root, or by `fyr adopt`), then `fyr install`. No registration, no manifest edits, no code. The installer maps each directory to its place under `~/.gemini/config/`.

- **R6** — Development never touches the real home.
  <!-- provenance: the operator, 2026-09-03; enforced by: TestEvalRefusesWithoutHome, TestEvalRefusesItsHome, AGENTS.md -->

  Every test and every development run of the installer uses `--home` with a scratch directory. Deploying to the operator's real `$HOME` is the operator's action, except on a machine whose `DEPLOY-local` record § Operator steps records the operator's standing permission to keep it current: there a session's checkpoint ends with `fyr install` from a clean, pushed checkout into the real home. (ADR-078.)

- **R7** — Projects remember and stay resumable.
  <!-- provenance: the operator, 2026-09-03; enforced by: TestAddGetEditList, TestExportByteStable, TestLoadReplacesRowsFromAChangedFile, TestEveryUnexportedKindStaysOut, TestStateDirHasOneHome, TestReportStaysOutOfTheProject -->

  Every project keeps its scratch in `.agents/scratch/` (gitignored), its root docs (`AGENTS.md`, `PRD.md`, `SDD.md`, `TDD.md`, `TODO.md`) in the checkout so work can continue with or without `fyr`, and its trail as records in the brain store (`~/.config/fyr/brain.db`): plans with task checkboxes, reviews, test logs, changes, handoffs, numbered bugs, ADRs, retros, learnings, specs, deploy and testing guides. They are written and read through `fyr record` and searched with `fyr search` directly in the brain store without writing to the checkout; when the operator wants to move or snapshot a project's trail, `fyr record export` writes `.agents/trail.jsonl` and `fyr record sync` loads it into the store on the target machine. Its memory is `memory` records in the same store, local to the machine and never exported. The harness's own state (manifest, the brain store, the global search index, the metrics store) lives in `~/.config/fyr/` and nowhere else. `fyr auto`'s reports stay on the machine (R3). (ADR-015, ADR-063, ADR-091.)

- **R8** — One delivery channel, and it is `fyr`.
  <!-- provenance: the operator, 2026-09-17; enforced by: TestHarnessMap, TestGlobalOnlyKinds, TestEveryUnexportedKindStaysOut, TestUpdateFromZipVerifiedAndTampered, TestDeliverySpecCurrent, TestKickoffBuilder, TestKickoffRubricAndAsks, TestRunnerChoice, TestWorkerBranchCleanup, TestWorkArgsUnchangedByAuto, TestTasksKickoffTemplates, TestTasksTriggers, TestTasksRedactedLearningInput, TestEvalRerunTriggers, TestEvalGate -->

  The harness reaches a machine one of three ways: a checkout the operator owns; a release's `fyr` binary with the harness built in; or a zip of the repository that the operator downloads with their own credential and passes to `fyr update --from-zip <file>`. Each is kept current with `fyr update`: the checkout and the binary as today, and a zip place by the operator repeating the download and `--from-zip`. There is no other channel — no vendored mirror inside a consumer project, no per-project copy, no service. A project that wants the harness uses `fyr`; this repository names no consumer project and depends on none. Nothing flows back: no verb but those named here sends the machine's corrections, proposals, memory or metrics anywhere; `feedback` and `proposal` records are global only, `memory` records are never exported, and `fyr record` refuses the first two in a project, and four things are sent by design: to the model of the CLI the machine already uses: the dreamer's redacted prompt (R3), and the runs of `fyr eval` and the workers of `fyr work`, which only the operator's own session starts or `fyr auto`, which the operator turned on (R3), and which send a sandboxed clone's prompts and the files its agent reads, unredacted, as any session of that CLI does, and, for `fyr auto`'s learning tasks, the conversations, memory, proposals and metric numbers `fyr` gives a worker, through the dream's redactor first; and to skills.sh and the npm registry, the search of a `fyr auto` worker looking for a missing skill, its query words unredacted. `fyr auto`'s workers run in docker when `fyr work`'s docker preflight passes and otherwise on the host, as the operator's uid, from the timer, at every level; check c and `auto.json`'s watch are tripwires, not containment, and the report names the runner and why. With either runner a worker's agent has `command(*)` and the network, so this list is what is designed, not what is confined (ADR-065, ADR-076, ADR-090). Experience reaches the harness only through the operator's own hands in their checkout, or an eval-gated `fyr auto` commit to that checkout's local branch (R9), which those hands push. (ADR-030, ADR-033, ADR-038, ADR-062, ADR-090.)

- **R9** — Three procedures, set in stone.
  <!-- provenance: the operator, 2026-10-24; enforced by: TestHarnessMap, TestUpdateNeverInstallsDirtyTree, TestUpdateFromReleaseReplacesAndInstalls, TestUpdateFromZipVerifiedAndTampered, skills/fyr-preflight/SKILL.md, TestEvalGate -->

  The harness is operated by three procedures and no others, drawn in `README.md` § How it works:

  - **Install:** a place either clones `fyr` with the operator's own credential and runs `fyr install`, or downloads a release's `fyr` binary with that credential — `gh release download`, `go install` over SSH, or the Releases page — and runs `fyr install`, which installs the harness built into the binary. Either way installed files go into `~/.gemini/config/` and no repository is created.
  - **Update:** the operator edits, verifies, commits and pushes `main` in their checkout, or `fyr auto` at level `harness` commits an eval-gated change to the checkout's local branch, which the operator pushes. A checkout place runs `fyr update` when the operator decides — fetch, refuse a dirty checkout, fast-forward, rebuild, reinstall. A binary-only place runs `fyr update`, which downloads the newest release, checks it against the release's `SHA256SUMS`: integrity, not authenticity — trust rests on the operator's GitHub credential and HTTPS, as for a checkout place — replaces the binary and reinstalls; it changes only when a release is cut. Nothing is pushed to a machine.
    - **Zip place:** the operator downloads the repository zip by hand and runs `fyr update --from-zip <file>`. It unpacks the zip into a temporary directory, refuses any entry that would leave it, installs that tree with the running binary, and deletes the directory. Nothing is fetched, no repository is created, and nothing in the zip replaces the binary. When the release's `SHA256SUMS` sits beside the zip, the zip is checked against it and refused on a mismatch; a zip without it is installed marked `UNVERIFIED`.
  - **Release:** `/fyr-preflight vX.Y.Z`, from the operator's own turn, gates the tree, pushes an annotated tag on `main`, and publishes that tag's binaries and a zip of its tree (`git archive`), with their `SHA256SUMS`; no key is needed, so any machine with the operator's GitHub credential can cut one. Checkout places follow `main`; binary-only places update to the newest release.

  The three procedures and the map change together, only with the operator's explicit approval, an ADR, and one commit carrying the code, the docs and the map. (ADR-031, ADR-033, ADR-038, ADR-039, ADR-040, ADR-041, ADR-053, ADR-062, ADR-090; each quotes the operator's approval of its text.)

- **R10** — One behaviour on every place.
  <!-- provenance: the operator, 2026-10-24; enforced by: TestTimerMacOS, TestAgySessionMac, TestAgySessionLinux, TEST-2026-09-04-verify-mac-real-home, TestRunnerChoice, TestAutoOnWritesTheConfigAndTheTimer -->

  Every harness feature is set up and runs the same at every place, whichever of the three ways in (R8) it came by, and on every operating system the operator runs it on (Linux, macOS). What only the Antigravity CLI's own runtime controls, and neither the context nor `fyr` can reach, is a Known limit below. `fyr auto`'s runner depends on the build, and its level `harness` needs a checkout, so neither is the same at every place (R3, R8, ADR-090). (ADR-047, ADR-062.)

## Known limits

- **Antigravity global rules are one 24,000-byte block.** CLI 1.2.7 builds one block from `~/.gemini/config/rules/*.md` and cuts it at 24,000 bytes with a `<truncated N bytes>` marker; a second file costs the first one room, and what falls past the cut is dropped without a marker (BUG-085, measured 2026-09-21); files that fit under the cut all load (measured 2026-10-05: context and `critical-thinking.md`, 16,993 bytes; ADR-051; the vendor page, read 2026-09-30, now says 24,000 bytes per file plus a 20,000-token budget across all always-on rules, so the discrepancy with the measured single block stands as measured). The deployed context is pinned under 22,000 bytes by a test, and `rules/` files share the block.
- **Antigravity global rules path.** The CLI's customization root is `~/.gemini/config/`; rules there are documented for the workspace form (`.agents/rules/*.md`) and by analogy for the global one. Verified on the Linux box 2026-09-03 (`TEST-2026-09-03-verify-real-home` (`fyr record get`)): the CLI reads rules, skills, and agents from there. Confirmed on the Mac for Antigravity on 2026-09-04 (`TEST-2026-09-04-verify-mac-real-home`).
- **Antigravity tool names cannot be enumerated.** An unrecognised name in an agent's `tools:` hangs the subagent, so `fyr install` fails on any tool name it does not know rather than guessing.
- **Antigravity IDE is out of scope.** Only the `agy` CLI is targeted; the IDE's global paths are unverified.
- **`fyr work` on macOS and `--runner auto` host fallback.** On macOS, safety check e (`leftoverProcs`, `internal/sandbox/procs_darwin.go`) scans the operator's processes with `/usr/sbin/lsof` (`cwd`, `txt`) and `/bin/ps -Eww` (`HOME=<SB>` environment and command line) alongside the final process-group kill (`fyr eval` and `fyr work`, ADR-076, ADR-510), rather than Linux `/proc`. With `--runner docker` the session's processes live in Colima's VM and check e also lists the worker's container by its labels and fails the worker on one left running (ADR-079). Under the default `--runner auto`, a machine whose docker is not ready runs its workers on the host without container isolation; the stamp line names the host and why, and `/fyr-work` — both on a task list and on `/fyr-work PLAN-ID` — runs `fyr work --check`, passes `--runner`, and waits for the operator's go before a run that falls back to the host (ADR-504, ADR-507, ADR-510).
- **Antigravity has no compaction window a file can set.** A session compacts when the CLI decides; the session-sizing rule (`rules/session-sizing.md`, ADR-058) is the only mechanism that ends a session at its checkpoint.
