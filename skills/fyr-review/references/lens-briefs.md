## Parallel orchestration (`run_workflow` & CLI judge)

- **2+ lenses via `run_workflow`:** Invoke `run_workflow` with `ScriptPath` set to `<HOME>/.gemini/config/workflows/review_parallel.py` (expanded absolute `$HOME`, never literal `~` because the pre-hook validates `ScriptPath` with `os.Lstat`; `<repo>/workflows/review_parallel.py` also works in a harness checkout) and `Args: {"scope_text": "<verbatim scope text>", "scope_slug": "<scope>", "date": "<YYYY-MM-DD>", "lenses": [...]}` (plus `"judge_criterion"` for `--judge`, `"verify_tiers"` for `--tests`, or optional `"cross_family"` / `"judge_model"` overrides). In live `run_workflow` turns (`CONVERSATION_ID` set, no `FYR_WORKFLOW_MOCKS`), `review_parallel.py` resolves cross-family routing via `fyr models --pick judge --json` and runs guarded lenses (`reviewer`, `security`, `verifier`) via isolated headless `agy -p --model <id>` (`--disable-slash-commands --output-format json --json-schema`), rejecting non-empty `denied_actions` and falling back to native `model="pro"` when quota picks Gemini or headless execution fails (`explorer` stays on native `model="flash"`). It automatically merges `--code` + `--docs` into one dispatch and returns JSON per lens. Use direct `invoke_subagent` for 1-lens runs or Round 2 `send_message` resumes.
- **Deterministic CLI cross-family judge:** Run `fyr gate --judge "<criterion>" [--judge-model <id>] <worktree-or-branch>` or `fyr land --judge "<criterion>" [--judge-model <id>] <branch>` for an isolated, read-only `Network: true` `agy -p` verdict over the git diff and `verify.stamp` summary (logged to `metrics.db` `judge_verdicts`).

## Docs brief (`--docs`) — pass verbatim as one numbered list

1. Keep your report template; report only. Alone, mark every criterion `n/a — docs lens`; inside a `--code --docs` dispatch the code brief fills the criteria and this list is the `## Docs lens` section.
2. Compare the scope with `README.md`, the `spec` records, `GUIDE-testing`, the `DEPLOY-*` records and the newest `change` record (`fyr record list --kind <kind> --open`, then `fyr record get`). Each finding is a statement that no longer matches the code, or a changed interface, command or deploy step the docs do not mention.
3. Run `fyr check` at the checkout's root. It reads the working tree, so for a range whose head is not HEAD say so and mark its findings unverified. It reports what the docs name and the tree lacks — a `fyr` verb, subverb or flag; a path or `path:line`; a spec whose code was committed to since the spec; a requirement with no `enforced by:` site that resolves; a requirement or component missing from the `SDD.md` or `TDD.md` trace — and exits 1 when it finds any. A finding on a line the scope changed, or on a spec or requirement the scope's code touches, is a docs finding; list every other one under `Pre-existing (fyr check)`, outside the scope's verdict. Each `note:` line is a part it did not check: quote it.
4. Before reading by hand, run `bash <review skill directory>/scripts/restatement-grep.sh -i -- <key words of each changed claim>` (the skill directory: `~/.gemini/config/skills/fyr-review` or the project's `.agents/skills/fyr-review`, the first that exists). It lists every living file that restates a claim, records and vendored skills excluded, so the first round reads every copy.
5. For every rule or statement the scope changes or removes, `git grep` its old wording in the living docs as they are at the scope's head (the working tree, or `<b>` of a range; a symlinked directory is searched at its target, less any skill or catalog path the project lists as vendored): `README.md`, `AGENTS.md`, `.agents/{rules,skills,agents,commands}/`, the `spec`, `guide` and `deploy` records (`fyr search <old wording> --kind spec`, `--kind guide`, `--kind deploy`), the project's test suites as its `AGENTS.md` Testing section names them (a `GUIDE-eval` record's rows, `web/e2e/`, and `*_test.go` beside a changed file), plus any paths the project's `AGENTS.md` adds. 7. A claim you could not check is listed as unverified.
8. Check touched or newly added explanatory docs (`README.md`, `SDD.md`, `TDD.md`, `SPEC-*`, `GUIDE-*`, `DEPLOY-*`, `docs/*.md`) against `~/.gemini/config/skills/docs-ste100-80/SKILL.md` (or `.agents/skills/docs-ste100-80/SKILL.md`): flag walls of prose or passive/filler wording, missing `Note`/`Caution` callouts before destructive commands, missing BLUF (Bottom Line Up Front), multi-component or multi-step flow sections lacking a Mermaid diagram (`mermaid-syntax`), uncollapsed > 12-row reference/schema tables that belong in `<details>`, or broken Mermaid syntax and relative links (`low` for style/airiness gaps, `medium` for missing safety callouts, broken links, or invalid diagrams).
