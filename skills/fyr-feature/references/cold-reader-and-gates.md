# Cold-Reader Brief, Gate Rule, and Build Details

Reference for `skills/fyr-feature/SKILL.md` Steps 3–6.

## Gate rule (waivers and headless runs)

For the pre-build interview and standalone invocations of skills that cite this gate rule (`fyr-bug`, `fyr-review`; inside a `fyr-feature` build, `/fyr-swarm`, or handed Kickoff, `ADR-517` overrides mid-build/review-cap asks by settling in-scope items as D-rows and deferring closed-set items to `Next Steps`):

- A gate holds unless the operator's own words in the **same turn** waive it (invocation arguments count, e.g. `"The scope is confirmed as written; do not ask me anything"`). A bare invocation or waiver from an earlier plan/session never waives a gate.
- When waived in the invocation turn, settle recommended defaults as dated D-rows (`by: planner`), defer any closed-set item (secrets, unapproved `PRD.md` edits, new structural ADRs, `who: user` boxes, releases, deploys, unapproved real-home installs) to handoff `Next Steps`, and tick the cold-read box without asking.
- When no reply can arrive at an unwaived gate (a print-mode run like `agy -p`, or a user who said they will not answer), write the questions with recommended options into the handoff's `Next Steps` (creating the handoff if absent) and stop before editing source.

## Verbatim cold-reader dispatch brief (Step 3)

Dispatch `reviewer` with **only the plan file**, nothing from the conversation, a budget of 15 tool calls, `"write the artifact early, then update it"`, and this verbatim brief:

> You are a fresh reader with no prior context. Read this plan and the code surfaces it names. Answer five things. (1) Gaps: what must be decided before implementation starts that the plan does not decide — interfaces, failure modes, scope edges, misunderstandings of existing code (cite file:line), a Verification or E2E criterion that names an implementation choice, a test fixture in a verify clause that does not produce the condition it claims (say which syscall or code path refuses it), an assumption asserted but not checked, a task changing a command, flag, endpoint, config key or deploy step with no docs clause, a `PRD.md` item the plan touches and does not cite, and every term, acronym or name the plan uses without defining it or citing a file (the naive-reader check). (2) Scope: what does the plan build that the request in `## Why` did not name — an extra endpoint, a second shape for the same operation, configuration for values that never vary? Each is a gap unless a D-row says who asked for it. (3) Readiness: could a first-pass implementer ship this without asking the author a question? List every question you would have to ask, and mark each BLOCKING (two careful implementers would build different things) or NON-BLOCKING (the plan states a default, or a reasonable implementer decides it alone). (4) Sizing: could a fresh session finish and verify each phase from this plan alone? Name the phase that could not and why; it counts as a gap. (5) Parallelism: does every multi-phase worker phase carry a `files:` line (and on a `workers: yes` plan, `model:`, `base-check:`, `judge:` and `judge-model:`), which phases could run at once without sharing a file (two `files:` entries intersect when they are equal, or when one is a directory ending in `/` that is a prefix of the other), and is an `after:` missing? Report at most 10 findings and questions in total across (1)–(5), ranked blocking and high-severity first, one or two sentences each, keeping the report under 80 lines. End with `design ready` only if you have zero gaps, and `implementation ready` only if you have zero BLOCKING questions; otherwise `design needs revision` / `implementation not ready`.

## Step 4–6 execution notes

- **Mid-phase state & findings:** At any stopping point inside a phase, append `— in progress: <where it stopped>; blocker: none | <what>` to the active box and delete that note once ticked. File newly found blockers as a new box above the blocked task ending `— found in: <task>`, bugs via `fyr-bug`, and deferrable work as a single line under Scope's Follow-ups ending `found in: <task>`.
- **Per-layer verification (Go + web stack):** Apply migration and inspect schema -> package tests with `-race` -> API hit with `curl` -> real browser walkthrough (golden path + edge case) -> local container build/run (`docker build`, `docker run`, `curl /healthz`).
- **E2E vs deploy:** Service e2e builds/runs the container and hits `/healthz` + one real request; frontend e2e walks the golden path + one edge case (empty, error, unauthenticated) in a real browser. Cloud smoke runs inside `/fyr-preflight` via `DEPLOY-gcp`, never as a substitute for local e2e.
- **Chat report at Done:** Check `git describe --tags --abbrev=0` or `fyr version` live before citing any version. Lead with a 1–2 line verdict, files by phase, tests added, cold-reader result, review outcome with verbatim rebuttals, e2e result, **Autonomous Decisions Log** (every `by: implementer` or `by: lead` D-row), deferred closed-set items, and a fenced `Next prompt:` block when work remains.
